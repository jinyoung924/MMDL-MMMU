## 0. Quickstart

```bash
pip install -r requirements.txt

# 베이스라인: seed 0~4로 900문항을 5번 돌리고 평균 ± 표준편차를 낸다 (RTX 4090 기준 약 6.5시간: seed당 약 77분).
# 모델/데이터는 pinned revision으로 자동 다운로드. 이미 끝난 seed는 건너뛰므로 중간에 끊겨도 이어서 돈다.
bash eval.sh

# fine-tuned 체크포인트 재평가: 모델 경로와 출력 폴더만 바꾼다. 나머지는 전부 동일.
bash eval.sh /abs/path/to/finetuned_ckpt results_ft

# 1회 실행만 (smoke test 등)
python run_eval.py --seed 0 --out results/seed0
```

확정된 기본값: `--prompt-style cot --max-new-tokens 8192 --max-model-len 24576 --batch-invariant 1`, seed 0~4
(각각 §2, §3에 실측 근거). `ablation/`에 그 근거가 된 실행 결과가 그대로 들어 있습니다.

산출물:

| 파일 | 내용 |
|---|---|
| `results/seed{s}/predictions.jsonl` | 문제 1건당 1줄 — 프롬프트, 원문 응답, 파싱 결과, 정답, 정오, 잘림 여부, fallback 추측 여부, 메타데이터(세부 분야·이미지 유형·난이도) |
| `results/seed{s}/scores.json` | 그 실행의 과목별/종합 점수 + **그 실행에 쓰인 전체 config** |
| `results/scores.json`, `results/table.md` | 5 seed 집계: 과목별·종합 평균 ± 표준편차, 문항별 정답 횟수 분포. §5 표가 이것 |

> **왜 모델 경로 하나만 바꾸면 되는가**: 프롬프트·생성 파라미터·파싱 로직·데이터 revision이 전부
> `run_eval.py`의 기본값에 고정되어 있고, 실제 사용된 값은 `scores.json`의 `config`에 매 실행마다 기록됩니다.
> `analyze.py aggregate`는 seed 외의 config가 하나라도 다른 실행들은 **합치기를 거부**합니다. 두 평가의 `config`가
> `model`만 다르면, 점수 차이는 체크포인트 차이라고 말할 수 있습니다. 이게 이 과제의 실제 목적입니다.

## 1. 환경 / 재현성

| 항목 | 값 |
|---|---|
| 모델 checkpoint | `Qwen/Qwen3-VL-4B-Instruct` revision `ebb281ec70b05090aa6165b016eac8ec08e71b17` |
| 데이터셋 | `MMMU/MMMU` revision `98e6ac0cb9b7b2cd2c991b85a50762edc4aedc68`, split `validation`, 30개 config 전부 |
| 추론 백엔드 | **vLLM 0.24.0** (offline `LLM.generate`, V1 engine) |
| dtype | `dtype="auto"` → 리포지토리 기본값 bf16 (별도 양자화 없음) |
| 사용 GPU | NVIDIA GeForce RTX 4090, 24564 MiB |
| 실측 peak VRAM | **23,754 MiB** / 24,564 MiB (`nvidia-smi` 5초 폴링 최댓값) — 아래 주의 참고 |
| 총 소요 시간 | 1회(900문항) **76~78분**, 5 seed 합계 **약 6.4시간** (모델 로드/컴파일 제외한 생성 구간, 결정적 모드). 일반 모드는 1회 약 45분 |
| 의존성 | [`requirements.txt`](../requirements.txt) — Python 3.11.15 / CUDA 13.0 / torch 2.11.0+cu130 / transformers 5.13.0 / datasets 5.0.1 |
| 실행 커맨드 | `bash eval.sh Qwen/Qwen3-VL-4B-Instruct results` (내부적으로 `python run_eval.py --model <MODEL> --seed <s> --out <OUT>/seed<s>`를 s=0..4로 호출한 뒤 `python analyze.py aggregate <OUT>/seed*`) |

**추론 백엔드로 vLLM을 고른 이유**: 900문제 × 평균 1개 이상의 이미지를 `transformers.generate()`로 한 건씩
돌리면 GPU가 대부분의 시간 동안 놀게 됩니다. vLLM은 continuous batching + paged KV cache로 여러 문제의
prefill/decode를 겹쳐서 처리하므로, 같은 24GB 카드에서 전체 실행 시간이 한 자릿수 배 단축됩니다.
부수 효과로 KV cache 예산(`--gpu-mem-util`)이 명시적 knob이 되어 VRAM 한도를 문서화하기 쉬워집니다.
단, continuous batching은 **실행마다 배치 구성이 달라져 같은 seed로도 출력이 달라지는** 부작용이 있어
배치 불변 모드를 켰습니다(§3.1).

**peak VRAM 읽는 법 주의**: vLLM은 `gpu_memory_utilization=0.90` 목표치까지 KV cache를 **미리 할당**합니다.
따라서 23,754 MiB는 "이 워크로드가 필요로 한 양"이 아니라 **"우리가 쓰라고 허락한 양"**에 가깝습니다.
(이 값은 동일한 `gpu_memory_utilization=0.90` 설정의 ablation 실행 중 측정했습니다. 이 knob이 값을
결정하므로 실행별로 유의미하게 달라지지 않습니다.) 24GB에서 돌아간다는 것만 확인된 값이고,
더 작은 카드에서는 이 knob을 낮추면 됩니다 — 단 `max_model_len=24576`을 담을 KV cache는 남아야 합니다.

**모델/데이터는 repo에 커밋하지 않습니다.** 둘 다 `huggingface_hub` 표준 캐시(`~/.cache/huggingface`)로
받고, revision을 코드 기본값으로 pin 했습니다 (`run_eval.py`의 `MODEL_REV` / `DATA_REV`).

## 2. 프롬프트

**실제 모델에 들어간 프롬프트 전문** (변수는 `{}`, 최종 채택 = `--prompt-style cot`):

객관식 (multiple-choice):
```
{question}
(A) {option_A}
(B) {option_B}
(C) {option_C}
...
Think step by step, then give your final answer on the last line in exactly this format: "Answer: X"  (X = the letter of the correct option).
```

주관식 (open):
```
{question}
Think step by step, then give your final answer on the last line in exactly this format: "Answer: <single word or phrase>".
```

이 텍스트가 `Qwen3VLProcessor.apply_chat_template(..., add_generation_prompt=True)`를 거쳐 단일 user turn으로
감싸집니다. **system prompt는 넣지 않았습니다.**

- **출처**: 질문·선택지 조립부(`(A) ...` 줄 형식)는 MMMU 공식 저장소
  [`mmmu/utils/data_utils.py`](https://github.com/MMMU-Benchmark/MMMU/blob/main/mmmu/utils/data_utils.py)의
  `construct_prompt()`를 그대로 따랐습니다. **마지막 지시문 한 문장만 직접 설계**했습니다.
  원본인 MMMU 공식 지시문(`Answer with the option's letter from the given choices directly.`,
  [`mmmu/configs/llava1.5.yaml`](https://github.com/MMMU-Benchmark/MMMU/blob/main/mmmu/configs/llava1.5.yaml))도
  **같은 조건에서 실측**했고, 그 결과가 아래 교체 근거입니다.

- **왜 공식 지시문을 바꿨는가 (실측 근거)**: MMMU 공식 지시문은 "바로 답하라"고 하지만
  **Qwen3-VL-4B는 이 지시를 따르지 않고 계산 과목에서 CoT를 시작해 버립니다.** 그 결과 응답이 생성 예산에서
  잘리고, 잘린 응답은 파서가 답을 못 찾아 무작위 추측으로 떨어집니다. 같은 생성 예산(8192)에서 두 지시문을
  비교하면:

  | 프롬프트 | 실행 | 종합 | 잘림 | 무작위 추측 |
  |---|---|---|---|---|
  | MMMU 공식 (`answer directly`) | 1회 (일반 모드) | 59.78 | 83 | 7 |
  | 직접 설계 (CoT + 답 형식 강제) | 1회 (일반 모드, 같은 시기) | 65.44 (64.22¹) | 135 | 16 |
  | **직접 설계 (CoT + 답 형식 강제)** | **5 seed 평균 (최종 설정)** | **64.93 ± 0.94** | 137.8 | 13.4 |

  ¹ 괄호는 파서 버그 수정 전 점수(§4). 공식 지시문 쪽은 `Answer:` 태그 파싱을 쓰지 않으므로 버그의 영향이 없습니다.

  CoT 5회 평균이 공식 지시문 1회보다 5.2점 높고, 이는 단일 실행 간 표준편차(0.9~2점)보다 큽니다. 즉 모델이
  어차피 추론을 하므로, **추론을 금지하려 애쓰는 것보다 추론을 허용하되 마지막 줄 형식을 강제하는 쪽**이
  유리합니다. 두 변형은 **마지막 한 문장을 제외하면 완전히 동일**하고(`build_prompt()`의 `style` 인자) 폴백
  파서도 공유하므로, 이 차이는 지시문의 효과입니다. (공식 지시문은 1회만 돌렸으므로 그쪽의 분산은 측정하지 않았습니다.)

- **설계 검증**: 완주한 응답은 마지막에 `Answer:` 줄을 씁니다. 태그 미검출은 잘린 응답에서만 생깁니다
  (cot@4096: 미검출 201건이 전부 잘린 응답. 잘린 응답은 203건으로, 2건은 `Answer:` 줄을 쓴 뒤 계속 쓰다가 잘림).
  예외는 선택지 내용이 알파벳인 문항에서 모델이 이미지 라벨을 답으로 쓴 경우뿐입니다(§4 알려진 한계).
  즉 형식 지시 자체는 완주만 하면 지켜집니다.

### 2.1 이미지 배치 규칙 (`<image N>` 처리)

MMMU 데이터는 질문/선택지 텍스트 안에 `<image 1>` 같은 플레이스홀더를 두고, 실제 PIL 이미지는
`image_1` … `image_7` 컬럼에 따로 담습니다. **선택지 자체가 이미지인 문항도 있습니다**
(예: `validation_Music_1`의 options = `['<image 2>', '<image 3>', '<image 4>', '<image 5>']`).
따라서 이미지를 프롬프트 맨 앞에 몰아넣으면 "어느 선택지가 어느 그림인지" 정보가 사라집니다.

규칙 (`run_eval.py`의 `interleave()`):
1. 완성된 프롬프트 텍스트를 `<image N>` 위치에서 잘라, **등장 순서대로** 텍스트와 이미지를 번갈아 배치.
2. 행에 존재하지만 어떤 플레이스홀더도 참조하지 않는 이미지는 **버리지 않고 맨 뒤에 덧붙임**.
3. 플레이스홀더는 있는데 해당 이미지 컬럼이 비어 있으면 그 자리는 건너뜀.

## 3. 생성(Decoding) 설정

### 3.1 Sampling recipe — Qwen 공식값 사용

| 파라미터 | 값 |
|---|---|
| `do_sample` | `true` (greedy 아님) |
| `temperature` | `0.7` |
| `top_p` | `0.8` |
| `top_k` | `20` |
| `repetition_penalty` | `1.0` |
| `presence_penalty` | `1.5` |
| `seed` | `0, 1, 2, 3, 4` (5회 실행, 요청 단위 `SamplingParams(seed=s)` + 배치 불변 모드) |

- **출처 (두 곳에서 교차 확인)**:
  1. **pin한 revision의 저장소 파일 그 자체** — `Qwen/Qwen3-VL-4B-Instruct@ebb281ec`의
     `generation_config.json`: `{"do_sample": true, "temperature": 0.7, "top_p": 0.8, "top_k": 20, "repetition_penalty": 1.0}`.
     모델 제공사가 이 체크포인트에 직접 동봉한 값이므로 가장 권위 있는 출처입니다.
  2. [HuggingFace 모델 카드](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct) 의 권장 설정 —
     `generation_config.json`에 없는 `presence_penalty`를 **vision-language 과제용으로 1.5**로 명시
     (참고로 순수 텍스트 과제용은 temperature 1.0 / top_p 1.0 / top_k 40 / presence_penalty 2.0 로 다릅니다.
     MMMU는 VL 과제이므로 **VL 쪽 값**을 씁니다).
- **greedy를 쓰지 않은 이유**: 과제가 요구한 "제공사가 공식 문서화한 recipe"가 실제로 존재하고
  (위 1·2), 그 값이 `do_sample: true`입니다. greedy는 여기서 근거 없는 임의 변경이 됩니다.
- **sampling인데 재현성은 어떻게 확보하나 (2026-09-25 개정)**
  - **이전 판의 주장은 틀렸습니다.** 이전 판에서는 "요청 단위 seed를 고정하면 배치 구성이 달라져도 같은
    토큰열이 나온다"고 썼습니다. 실제로 같은 설정·같은 seed 0으로 900문항을 두 번 돌리자 **응답이 글자 단위로
    같은 문항은 32개**뿐이었고, 160문항의 정오가 뒤집혀 점수가 65.44 → 62.44로 달라졌습니다
    (`ablation/cot_8192_seed0_run1`, `ablation/cot_8192_seed0_run2`).
  - **원인**: seed는 샘플링 난수열만 고정할 뿐 logits는 고정하지 못합니다. vLLM은 continuous batching으로
    요청을 묶는데, 배치 크기·구성이 달라지면 bf16 행렬곱의 누산 순서가 바뀌어 logits가 미세하게 달라지고,
    temperature 0.7 샘플링이 그 차이를 다른 토큰 선택으로 증폭합니다.
  - **해결 1 — 배치 불변 모드**: vLLM 0.24.0의 `VLLM_BATCH_INVARIANT=1`은 행렬곱·softmax·RMSNorm 등을
    배치 구성과 무관한 결정적 커널로 바꿉니다(RTX 4090 = SM 8.9는 Triton persistent matmul 경로).
    `run_eval.py --batch-invariant 1`(기본값)이 엔진 시작 전에 이 변수를 켭니다. 효과를 대조 실험으로
    확인했습니다(`ablation/determinism_probe`): 같은 seed로 60문항 배치와 90문항 배치를 돌려 공통 60문항을 비교.

    | 모드 | 응답 글자 단위 일치 | 정오 뒤집힘 | 생성 속도 (글자/초) |
    |---|---|---|---|
    | 일반 | **0/60** (앞 200자까지 같은 것 39) | 10 | 4,681 ~ 5,642 |
    | 배치 불변 | **60/60** | 0 | 2,552 ~ 3,602 |

    비용은 약 1.6~1.8배 느려지는 것입니다.

    **900문항 전체 재현 검증** (`ablation/repro_seed0`): 공식 seed 0과 같은 설정으로 한 번 더 돌린 결과,
    **899/900개 응답이 글자 단위로 같았고 정오가 뒤집힌 문항은 0개, 점수는 64.33으로 동일**했습니다. 다른 1개
    (`Sociology_24`)는 약 1만 1천 자 응답의 7,600번째 글자 근처에서 문장이 갈라졌지만 최종 답과 정오는 같았습니다.
    즉 점수·정오 수준에서 완전히 재현됩니다(일반 모드에서는 같은 seed로 32/900). 단, 결정성은 **엔진 설정까지 같을 때**
    성립합니다. `max_model_len`만 바꿔도 끝난 응답의 96%만 같았습니다(§3.2의 16,384 실험).
  - **해결 2 — 5 seed 평균**: 결정성은 "같은 seed → 같은 결과"를 보장할 뿐, **샘플링 분산 자체는 남습니다.**
    seed만 바꿔도 종합 점수는 64.22~66.56(표준편차 0.94), 과목 점수는 최대 26.7점 폭(Biology)으로 흔들립니다(§5).
    그래서 공식 결과는 seed 0~4의
    평균 ± 표준편차로 보고하고(§5), fine-tuning 전후 비교도 같은 5 seed로 합니다. 5회 평균의 표준오차는
    단일 실행 표준편차의 약 1/√5입니다.

### 3.2 생성 예산 / 이미지 해상도

| 파라미터 | 값 |
|---|---|
| `max_new_tokens` | `8192` |
| `max_pixels` (per image) | `1280 × 32 × 32 = 1,310,720` px → **이미지당 최대 1,280 vision token** |
| `min_pixels` (per image) | `4 × 32 × 32 = 4,096` px |
| `max_model_len` | `24576` |
| `limit_mm_per_prompt` | `{"image": 7}` |
| `gpu_memory_utilization` | `0.90` |

**이미지 해상도 근거.** Qwen3-VL은 `patch_size=16`, `merge_size=2`이므로 vision token 1개가 원본
`16×16×2×2 = 1,024` px에 대응합니다 (Qwen2-VL의 28px 격자와 다릅니다 — 28 단위를 그대로 쓰면 예산 계산이
틀어집니다). pin한 revision의 `preprocessor_config.json` 기본값은 `longest_edge = 16,777,216` px,
즉 **이미지 하나당 16,384 vision token**입니다. MMMU는 한 문항에 이미지가 최대 7장까지 들어가므로 기본값
그대로면 프롬프트 하나가 11만 토큰을 넘길 수 있고, 24GB 4090에서는 감당이 안 됩니다. 그래서 이미지당
1,280 token으로 캡을 씌웠습니다. 이 값의 근거는 데이터 실측입니다 — MMMU val 이미지 982장의 픽셀 수는
**중앙값 198k px, p95 1.52M px**이고, 1.31M px 캡을 넘는 이미지는 **59장(6.0%, 58문항)**뿐입니다.
즉 94%의 이미지는 다운스케일 없이 통과하고, 꼬리쪽 큰 이미지만 줄어듭니다. 최악(7장)에도
7 × 1,280 = 8,960 vision token이라 `max_model_len` 안에 들어옵니다.

**캡이 성능을 깎는지 검증 (ablation, 2026-09-22)**: 캡에 걸리는 문항의 정확도가 낮아서(아래 표 마지막 두 줄)
캡이 원인인지 확인했습니다. `min_pixels = 256·32²`, `max_pixels = 2048·32²`(이미지당 최대 2,048 token),
`max_model_len = 32768`로 올려 900문항을 다시 돌렸습니다(`ablation/cot_8192_hires`). 비교 기준은 기존 설정의
3회 실행(seed 0 두 번, seed 1 한 번, 모두 수정된 파서로 채점)입니다.

- 가장 직접적인 증거: 실패 분석에서 태깅한 오답 50문항 중 고해상도 실행에서 맞힌 수(12)가 **seed만 바꾼 실행에서

- 결론: 큰 이미지 문항은 원래 어려운 문항(다중 패널, 복잡한 도면·악보)이고 캡은 원인이 아닙니다. 고해상도는
  이득 없이 `max_model_len`과 VRAM 부담만 늘리므로 **캡을 유지**합니다.

좌우하는 단일 파라미터**였습니다. 두 프롬프트 × 예산으로 900문제 전체를 재실행한 결과:

- 처음 골랐던 512는 **215건(24%)을 잘라먹었고**, 잘린 문항의 정확도는 27.4%로 완주 문항(61.5%)의 절반
  이하였습니다. 무작위 추측 108건도 **전부** 잘린 응답이었습니다(108/108). 즉 짧은 예산은 "모델이 틀린 것"이
  아니라 **평가 장치가 만들어낸 오답**을 대량 생산합니다.
- 인과관계 확인: 과목별로 `512에서의 잘림 건수`와 `512→4096 점수 상승폭`의 **상관계수 = 0.859**.
  가장 많이 오른 과목이 정확히 가장 많이 잘렸던 과목입니다(Materials 27/30 잘림 → +33.3점).
  반대로 **하락한 과목은 전부 잘림 0~2건에 하락폭이 3.3점(= 1문제)** 이라, 노이즈 수준입니다.
- **8192를 고른 이유 (2026-09-25 개정)**: 이전 판은 "mmmu는 4096→8192에서 점수가 오르지 않았고(60.00 → 59.78),
  CoT는 아직 오르는 중(62.11 → 64.22)"이라고 해석했지만, **두 차이 모두 단일 실행 간 표준편차(약 2점) 안**이라
  1회 실행으로는 판정할 수 없습니다. 8192를 택한 근거는 점수가 아니라 **잘림 감소**(CoT 203 → 135)입니다.
  잘린 응답은 결론이 없어 채점이 사실상 찍기가 되므로(잘린 응답 정확도 약 35%) 잘림 자체가 측정 오차원이고,
  8192는 그 비율을 15%로 낮추면서 1회 실행을 한 시간 안팎에 끝내는 절충점입니다.

**16,384로 늘리면 잘림이 회수되는가 (직접 측정)**: 이전 판은 "완주 응답 정확도(69%)가 예산과 무관하게
고정이므로 잘림을 없애면 종합이 약 69%가 된다"고 추정했습니다. 이 외삽은 **잘린 문항도 완주하면 완주 문항만큼
맞힌다**는 가정에 기대는데, 잘린 응답의 약 3분의 1은 같은 문장을 반복하는 루프라서 예산을 늘려도 끝나지 않고,
나머지도 한 문항을 수천 토큰 동안 헤맨 응답이라 같은 정답률을 기대할 근거가 없습니다. 그래서 추정 대신 측정했습니다. 공식 5 seed에서 한 번이라도 잘린 문항
224개를 Qwen 권장치 16,384 토큰(`--max-model-len 32768`)으로 seed 0·1에서 다시 돌렸습니다
(`ablation/cot_16384_truncated`). 배치 불변 모드에서는 8,192번째 토큰까지가 대부분 그대로 재현되므로(아래 주의),
이 실험은 **같은 응답을 이어서 쓰게 한 것**과 같습니다.

| 항목 | seed 0 | seed 1 |
|---|---|---|
| 8,192에서 잘린 응답 | 127 | 139 |
| 16,384에서 끝까지 씀 | 35 (28%) | 42 (30%) |
| 16,384에서도 여전히 잘림 | 92 | 97 |
| 8,192에서 루프였던 응답 중 끝까지 씀 | 2 / 35 | 2 / 47 |
| 새로 끝까지 쓴 응답의 정확도 | 60.0% | 59.5% |
| 종합 점수 (8,192 → 16,384) | 64.33 → 65.11 (**+0.78**) | 66.56 → 67.33 (**+0.78**) |

- 예산을 두 배로 늘려도 잘린 응답의 **70%는 여전히 잘렸고**, 루프는 사실상 끝나지 않았습니다(82건 중 4건).
- 새로 끝까지 쓴 응답의 정확도(약 60%)는 원래 끝까지 쓴 응답(70.3%)보다 낮습니다. 이전 판의 "잘림을 없애면
  약 69%" 외삽은 틀렸습니다.
- 종합 효과는 두 seed 모두 **+0.78점**입니다. 공식 수치와의 격차(2.47점)의 약 3분의 1입니다(§7).
- 비용: 이 224문항만 seed당 약 190분이 걸렸습니다(8,192에서는 900문항 전체가 약 77분). 5 seed 평가를 16,384로
  하면 실행 시간이 몇 배로 늘어나지만 이득은 +0.8점이라, fine-tuning 전후 비교용 파이프라인은 **8,192를 유지**합니다.
- **주의 (결정성의 범위)**: 8,192에서 끝난 응답이 16,384 실행에서 글자 단위로 같았던 비율은 96%(93/97, 81/85)였고,
  잘린 응답이 같은 내용을 이어 쓴 비율은 86%(108/127, 120/139)였습니다. `max_model_len`(24,576 → 32,768)이
  바뀌어 엔진 설정이 달라졌기 때문으로 보입니다. 배치 불변 모드의 결정성은 **엔진 설정까지 같을 때** 보장됩니다(§3.1).

## 4. 채점(파싱) 방식

- **사용한 파서**: MMMU 공식 저장소
  [`mmmu/utils/eval_utils.py`](https://github.com/MMMU-Benchmark/MMMU/blob/main/mmmu/utils/eval_utils.py)의
  `parse_multi_choice_response` / `parse_open_response` / `eval_open`을 **로직 변경 없이 `run_eval.py`에
  이식(vendored)**했습니다. 외부 의존성을 하나 더 늘리지 않고 파서 버전을 파일 안에 고정하기 위해서입니다.
  (유일한 변경: 아래 4단계 fallback이 발동했는지를 호출부가 알 수 있도록 플래그를 함께 반환 — 점수 계산에는
  영향 없음.)

- **0단계 (CoT 프롬프트 전용, 직접 구현)**: 응답에서 `Answer:\s*\(?\s*([A-Za-z])(?![A-Za-z])` 를 찾아
  **마지막 매치**를 최종 답으로 씁니다(모델이 도중에 "Answer: A일까?" 식으로 언급해도 마지막 줄이 이기도록).
  태그가 없거나 선택지 범위 밖이면 **아래 MMMU 공식 파서로 그대로 폴백**합니다. 두 프롬프트 변형이 완전히
  같은 폴백 파서를 공유하므로, §2의 프롬프트 비교에 파서 차이가 섞이지 않습니다.

- **0단계 정규식의 버그와 수정 (2026-09-22)**: 처음 버전 `Answer:\s*\(?\s*([A-Za-z])\s*\)?`는 `\s*`가
  줄바꿈까지 건너뛰어서, 응답이 `Final Answer:⏎Answer: C`로 끝나면 둘째 줄 **"Answer"의 A**를 답으로
  읽었습니다. 첫 seed 0 실행에서 이 패턴이 16건, 그중 **모델은 정답을 썼는데 A로 읽혀 오답 처리된 문항이
  12건**(반대 방향 1건)이었습니다. 수정은 잡은 글자 뒤에 알파벳이 이어지면 안 된다는 조건
  `(?![A-Za-z])` 하나입니다.
  - 검증: 900개 응답 전부를 "줄 첫머리의 마지막 `Answer: X`"라는 독립 기준으로 다시 뽑아 비교해 불일치 0건.
  - 수정 전에 돌린 ablation 실행은 **저장된 응답을 수정된 파서로 재채점**해 표기합니다. 재채점이 실제 코드
    실행과 달라질 수 있는 경우(옛 정규식만 유효 글자를 잡아 폴백 경로가 바뀌는 응답)는 0건으로 확인했습니다.
    원래 점수는 괄호로 병기합니다.

- **객관식 동작 순서** (0단계가 실패했을 때. 앞 단계에서 후보가 나오면 거기서 멈춤):
  1. 응답 양끝 구두점을 제거하고 양쪽에 공백을 덧댐.
  2. `(A)` 처럼 **괄호 친 글자**를 찾음.
  3. 없으면 ` A ` 처럼 **공백으로 둘러싸인 단독 글자**를 찾음.
  4. 그래도 없고 응답이 5단어를 넘으면, **선택지 본문 텍스트**가 응답에 등장하는지로 역추적.
  5. 끝내 못 찾으면 `random.choice(all_choices)` — 즉 **무작위 추측**.
  6. 후보가 2개 이상이면 **응답에서 가장 뒤쪽(`rfind`)에 등장한 것**을 최종 답으로 봄
     (모델이 "A일까 B일까… 답은 B" 식으로 말하는 패턴을 잡기 위함).

- **주관식 동작 요약**: 응답을 문장/줄 단위로 쪼갠 뒤 `is `, `therefore `, `answer `, `=` 같은 단서 뒤의
  **가장 짧은 조각**을 답 후보로 뽑고, 거기서 숫자도 따로 추출합니다. 후보들을 소문자화/숫자는 소수점
  2자리 반올림으로 정규화한 뒤, 정답(복수 정답 허용)과 **부분 문자열 일치**하면 정답 처리합니다.

- **무작위 fallback에 대한 주의**: 5번이 발동하면 점수에 운이 섞입니다. 그래서 (a) 실행의 seed로
  `random.seed(seed)`를 고정해 재현 가능하게 만들고, (b) 발동 횟수를 `fallback_guess`로 세어 `scores.json`과
  매 문항의 `predictions.jsonl`에 남깁니다. 실측상 발동은 **전부 잘린 응답**에서만 일어납니다(완주한 응답은
  항상 `Answer:` 줄을 씀). 즉 이 수치는 파서 문제가 아니라 생성 예산 문제의 지표입니다.

- **알려진 한계: 선택지 내용이 알파벳인 문항**: 22문항은 선택지 내용이 알파벳 한 글자입니다. 대부분
  `(A) A (B) B …`처럼 기호와 내용이 같아 문제가 없지만, 2문항은 어긋납니다
  (`Basic_Medical_Science_17`: `(A) E (B) B (C) C (D) A`, `Music_15`: `(A) C (B) D (C) B (D) G`).
  모델이 이미지 속 라벨 "E"를 답으로 쓰면 선택지 기호로 해석할 수 없어 폴백으로 넘어가고, 라벨 "D"를 쓰면
  선택지 (D)로 읽힙니다. 파서에 의미 해석을 넣으면 규칙 기반 채점의 결정성이 깨지므로 고치지 않고 한계로 둡니다.

**계산식**
- 과목 Acc = seed별로 그 과목 30문항의 정답 비율을 구한 뒤 5 seed 평균. sd는 그 5개 값의 표본 표준편차.
- `Overall = mean(30개 과목 Acc)` (macro average). 과목당 정확히 30문항으로 균등하므로, 5 seed 전체 응답
  4,500개 중 정답 비율(micro)과 수학적으로 같습니다. seed별 종합의 평균과도 같습니다.
- seed별 종합: **64.33 / 66.56 / 64.78 / 64.22 / 64.78** → 평균 64.93, 표준편차 0.94.

**산술 정합성**: `run_eval.py`는 seed마다 macro와 micro를 **독립적으로** 계산해 `scores.json`에 남기고, 5 seed 모두
두 값이 일치합니다. 한 과목이라도 덜 로드되면 두 값이 갈라지므로, 30과목 × 30문항이 빠짐없이 들어갔다는 증거입니다.

**문항 단위 안정성** (5 seed 중 정답 횟수): 0회 166문항 / 1~4회 304문항 / 5회 430문항.
한 번이라도 맞힌 비율(pass@5)은 81.56%로 평균(64.93%)보다 16.6점 높습니다.

**해석 주의**: 과목 점수는 seed 간 표준편차가 최대 10.6점(Biology, 5 seed 범위 26.7점)이라, 과목 간 차이는
과목당 30문항에서 오는 불확실성과 함께 해석해야 합니다(§8).

| 우리 재현 결과 (5 seed 평균 ± 표준편차) | **64.93 ± 0.94** (seed별 64.22 ~ 66.56) |

## 7. 격차 분석

**Δ = −2.47점은 샘플링 노이즈로 설명되지 않습니다.** seed 간 표준편차가 0.94이고 5 seed 최고값(66.56)도
67.4에 못 미칩니다. 그래서 평가 설정의 차이를 후보로 두고 하나씩 검증했습니다.

1. **생성 예산 (격차의 약 3분의 1)**: 응답의 15.3%가 8,192 토큰에서 잘렸고, 잘린 응답의 정확도는 35.0%로 완주 응답
   (70.3%)의 절반입니다. 잘렸던 224문항을 Qwen 권장치 16,384로 이어 쓰게 하자 70%는 여전히 잘렸고(루프는 거의 끝나지
   않음), 종합은 두 seed 모두 **+0.78점**에 그쳤습니다(§3.2).
2. **이미지 해상도**: 캡을 풀어도 모든 픽셀 구간의 변화가 노이즈 범위였습니다(§3.2). 원인이 아닙니다.
3. **파서**: 우리 쪽 버그 12건은 수정했고, 수정 후 독립 기준과 불일치 0건입니다(§4). 공식 평가의 파서는 비공개입니다.
4. **문항 결함**: 실패 진단 표본에서 오답의 13%가 정답표 오류·정보 누락·선택지 중복이었습니다(`failure_diagnosis/`).
   공식 평가도 같은 문항을 풀므로 격차의 원인은 아니지만, 어떤 모델도 넘기 어려운 상한(val의 약 3%)을 만듭니다.
5. **남는 약 1.7점**: 공식 평가의 프롬프트·파서·예산이 공개되지 않아 원리적으로 검증할 수 없습니다. 우리 실험에서
   지시문 한 문장만으로 5점이 움직였으므로(§2), 비공개 프롬프트의 차이로 이 정도는 충분히 생길 수 있습니다.

## 8. 기타 특이사항 / 한계

- **남은 잘림** — 공식 5 seed에서 응답의 15.3%(seed당 127~146건)가 8,192 토큰에서 잘립니다. 잘린 응답의
  31%는 같은 문장을 반복하는 루프입니다. 권장치 16,384로 늘려도 70%는 여전히 잘리고 종합은 +0.78점에 그칩니다(§3.2).
- **sampling 기반 평가의 분산** — 종합 점수의 seed 간 표준편차는 0.94이지만, 과목 점수는 최대 10.6점(Biology,
  5 seed 범위 26.7점)입니다. 이전 판의 "과목당 노이즈 바닥은 약 3.3점(1문제)"은 틀렸습니다. 과목 간 차이와
  fine-tuning 전후 차이는 반드시 여러 seed의 짝 비교로 해석해야 합니다(`analyze.py compare`).
- **무작위 추측** — 5 seed 합계 67건(응답의 1.5%)이고 **전부 잘린 응답**에서 나왔습니다. seed별로
  `random.seed(seed)`를 고정해 재현 가능하고, `fallback_guess`로 세어 둡니다.
- **문항 결함** — 실패 진단 표본(두 실행에서 모두 틀린 문항 중 무작위 48개)에서 6개가 정답표 오류·정보 누락·
  선택지 중복이었습니다. val 900문항의 약 3%로 추정합니다. 사례와 근거는 [`failure_diagnosis/`](../failure_diagnosis/README.md).
- **데이터 다운로드 비용** — 과제 §1.2가 지정한 `load_dataset(config, split="validation")` 호출은
  각 과목의 **test split(약 3GB)까지 함께 받습니다**. 평가에 쓰이지 않지만, 스펙에 명시된 API를 그대로
  따르기 위해 우회하지 않았습니다. 채점자도 동일한 다운로드를 겪습니다.
- **fine-tuning 재평가 시 주의**
  - `max_new_tokens`가 점수를 가장 크게 좌우하므로(1회 실행 기준 53.33 ~ 65.44), 체크포인트 비교 시 이 값을
    **반드시 고정**해야 합니다. 고정하지 않으면, 더 장황해진 모델이 실제로는 좋아졌는데도 잘림이 늘어 점수가
    떨어지는 착시가 생깁니다.
  - 같은 5 seed, 배치 불변 모드로 평가합니다. `analyze.py`의 `aggregate`와 `compare`는 모델 경로 외의 평가 설정이
    다르면 합치기·비교를 거부합니다.
  - 망각을 잴 때는 "base가 맞힌 문항"을 **비교에 쓰지 않는 seed**로 골라야 합니다. 같은 실행으로 고르고 재면
    모델이 바뀌지 않아도 약 10점의 가짜 망각이 나옵니다(평균으로의 회귀,
    [`pilot_forgetting/README.md`](../pilot_forgetting/README.md)).
